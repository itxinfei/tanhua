## 一、P0 安全与并发问题

### 1.1 万能验证码无限制生效

| 项 | 内容 |
|---|---|
| 问题 | 验证码发送接口对任意手机号都返回固定验证码 `123456`，攻击者可登录任意账号 |
| 根因 | 测试便利代码未加范围限制，直接硬编码在业务逻辑中 |
| 修复 | 改为仅手机号对应的用户 ID=1（测试账号）时返回固定码，其他用户走真实短信验证码 |
| 预防 | **测试后门必须有白名单范围**（指定测试账号/指定环境变量开关），禁止全量生效；CI 中 grep 检查 `123456` 等魔法值 |

### 1.2 IdService 并发自增非原子化

| 项 | 内容 |
|---|---|
| 问题 | Redis INCR + 后续业务操作非原子，高并发下产生重复 ID |
| 根因 | 先 INCR 取值再写入业务数据，两步之间可被其他请求插入 |
| 修复 | 改用 Lua 脚本将取号与校验合并为 Redis 服务端原子操作 |
| 预防 | **Redis 多步操作必须用 Lua 保证原子性**；审查时检查 `opsForValue().increment()` 后是否紧跟条件判断 |

### 1.3 application.yml 明文密码入库

| 项 | 内容 |
|---|---|
| 问题 | 数据库/Redis/Nacos 密码明文写在配置文件中，随代码提交到仓库 |
| 根因 | 图省事直接写明文，未区分开发/生产环境的敏感信息管理 |
| 修复 | 改为 `${ENV_VAR:默认值}` 环境变量引用，`.env.example` 提供模板，真实值不入库 |
| 预防 | **密钥/凭证禁止入库**（用户红线）；CI 加 secret 扫描（如 trufflehog）；`git diff` 时人工检查新增配置项 |

## 二、P1 代码规范问题

### 2.1 System.out / 死代码 / 重复 import

| 项 | 内容 |
|---|---|
| 问题 | 生产代码残留 `System.out.println`、死代码 `main()` 方法、重复 import |
| 根因 | 调试代码未清理；IDE 自动 import 时重复添加 |
| 修复 | 删除所有 System.out（改用 SLF4J logger）；整段删除死代码 main 方法；去重 import |
| 预防 | **接入 SonarQube 或 IDEA 代码检查**；提交前 `git diff` 检查；后端可加 PMD/Checkstyle 规则禁止 System.out |

### 2.2 硬编码重置密码

| 项 | 内容 |
|---|---|
| 问题 | 管理员重置密码功能中 `md5Hex("123456")` 硬编码 |
| 根因 | 默认密码直接写在代码中，无法按环境配置 |
| 修复 | 改为 `@Value("${admin.reset-password:123456}")` 配置化，保留 dev 默认值 |
| 预防 | **业务可配置值一律走 @Value/配置中心**，代码中不出现魔法字符串；grep 检查 `md5Hex("` 等模式 |

### 2.3 HuanXinUser 历史命名残留

| 项 | 内容 |
|---|---|
| 问题 | 已从环信迁移到 WuKongIM，但 VO 类仍叫 `HuanXinUser`，误导维护者 |
| 根因 | IM 通道替换时只改了实现，未同步重命名对外模型 |
| 修复 | 新建 `ImCredential`（字段 provider/wsUrl 通用化），改 3 处引用，删除旧类，grep 验证零残留 |
| 预防 | **技术栈替换时同步重命名模型类**；审查时 grep 旧技术名（HuanXin/easemob）确认无残留 |

### 2.4 IM token 使用 MD5 哈希

| 项 | 内容 |
|---|---|
| 问题 | IM 用户凭证 token 用 `md5Hex(uid+salt)` 派生，MD5 已不安全 |
| 根因 | 初版实现选了 MD5，未随安全标准升级 |
| 修复 | 改为 `sha256Hex(uid+salt)`；存量用户下次取凭证时 WuKongIM 幂等注册自动恢复，无需手动迁移 |
| 预防 | **新代码禁止 MD5 用于安全场景**（密码/凭证/签名）；存量 MD5 需评估迁移成本后逐步替换；注意：用户登录密码的 MD5 因 DB 存量数据限制暂保留，属已知技术债 |

## 三、P1 基础设施接入

### 3.1 springdoc-openapi API 文档

| 项 | 内容 |
|---|---|
| 问题 | 12 个后端服务无 API 文档，前端联调靠口头沟通 |
| 根因 | 项目初期未接入文档工具 |
| 修复 | 根 pom 统一管理 `springdoc-openapi-starter-webmvc-ui:3.2.0`（**注意：v2.x 是 Spring Boot 3 线，v3.x 才是 SB4 线**）；10 个 WebMvc 服务加依赖；yml 配置 api-docs/swagger-ui 路径 |
| 预防 | **新项目脚手架阶段就接入 springdoc**；版本选型时查官方兼容矩阵，不凭记忆选版本 |
| 验证 | 启动服务后访问 `http://host:port/swagger-ui.html` |

### 3.2 PageInfo 构造参数不匹配（xfjy-match-service 编译错误）

| 项 | 内容 |
|---|---|
| 问题 | `new PageInfo<>(0, pageNum, pageSize, recommendUsers)` 编译报"无法推断类型参数" |
| 根因 | `PageInfo` 有 5 个字段（total/pageNum/pageSize/pages/records），`@AllArgsConstructor` 生成 5 参数构造函数，调用只传了 4 个，构造函数不匹配导致泛型推断连带失败 |
| 修复 | 补上缺失的 `pages` 参数：`new PageInfo<>(0, pageNum, pageSize, 0, recommendUsers)` |
| 预防 | **改 VO 类字段数后全量编译验证**；编译错误消息中的"无法推断类型参数"往往真实原因是构造函数/方法签名不匹配，先查参数个数与类型 |

### 3.3 前端 ESLint 接入

| 项 | 内容 |
|---|---|
| 问题 | xfjy-app 和 xfjy-admin 无 ESLint，代码风格无自动检查 |
| 根因 | 项目初期未配置 lint 工具链 |
| 修复 | 两项目接入 ESLint v9 flat config（`eslint.config.mjs`）：xfjy-app 加 eslint-plugin-vue + typescript-eslint（Vue SFC 中 TS 解析）+ uni-app 全局变量声明；xfjy-admin 加 eslint-plugin-vue + typescript-eslint；规则以 warn 为主避免存量阻塞 |
| 关键配置点 | ① `ecmaVersion: 'latest'` 支持可选链等新语法；② uni-app 全局变量（uni/getCurrentPages/plus/wx）需手动声明，否则 no-undef 误报；③ Vue SFC 中 `lang="ts"` 需配 `parserOptions.parser: tseslint.parser`；④ `@typescript-eslint/no-explicit-any` 从 error 降为 warn |
| 预防 | **新前端项目脚手架阶段就接入 ESLint**；存量项目接入时规则先全 warn，跑通后逐步收紧 |
| 验证 | `npm run lint` → 预期 0 errors（warnings 可存量）；`npm run lint:fix` 可自动修复格式类 warning |

## 四、通用预防清单（新增代码必须过）

1. **无魔法值**：数字/字符串常量一律提取为常量或配置项
2. **无 System.out**：统一用 SLF4J logger
3. **无明文密钥**：环境变量外置 + `.env.example` 模板
4. **无 MD5 安全用途**：新代码用 SHA-256 或 BCrypt
5. **Redis 多步操作用 Lua**：保证原子性
6. **技术栈替换同步重命名**：grep 旧名称确认零残留
7. **改 VO 字段后全量编译**：构造函数参数匹配验证
8. **前端 lint 先 warn 后收紧**：`npm run lint` 0 errors 为底线
