## 二、🔴 严重问题：CORS 允许任意来源携带凭证

**位置**：`CorsConfig.java`

```java
config.addAllowedOriginPattern("*");   // 允许任意来源
config.setAllowCredentials(true);      // 且允许携带凭证（Cookie / token）
```

**风险**：任意第三方网站在用户已登录状态下，均可借浏览器凭证直接调用 API（发动态、改资料等），构成 CSRF / 跨站数据泄露风险。

**修复建议**（二选一）：
1. 若前端仅用 `Bearer` Token（Sa-Token 默认）：`setAllowCredentials(false)` 并收窄 `addAllowedOriginPattern` 到前端域名白名单（如 `http://localhost:5173`、生产域名）。
2. 若确需凭证：至少将 origins 限定为前端已知域名，禁止 `*`。</n>
**规范关联**：AGENTS.md §二 安全防护要求“所有用户输入均视为高危，必须校验与异常捕获”；CORS 全开属于放宽同源策略的过度授权，应最小权限化。

## 三、🟡 配置错误：`globalcors` 路径写错 + 与代码重复

> ⚠️ **本节结论已于 2026-11-05 被证伪并纠正，见文末「七、复盘与纠正」**：
> `spring.cloud.gateway.server.webflux` 这一层**不是多余的错误层级，恰是 Spring Cloud 2025.x 的正确前缀**。
> 本节基于 Gateway 4.x 旧版前缀知识做出的「死配置」判断有误，照此删除直接引发网关全站 404 事故（提交 07a220c）。
> CORS 过度开放的安全发现本身成立、收敛到 `CorsConfig.java` 的方向也对；错的是前缀认知与删除操作误伤兄弟节点 `routes`。
> 阅读下文时请以第七节为准，勿再采信「应退回 `spring.cloud.gateway.globalcors`」的说法。

**位置**：`application.yml`

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          globalcors:   # 错误：多了一层 server.webflux，绑定不到 GatewayProperties
```

正确路径应为 `spring.cloud.gateway.globalcors.cors-configurations`。当前这段配置**完全不生效**（死配置）。

**衍生风险**：同时 `CorsConfig.java` 已用 `CorsWebFilter` 实现了一套 CORS。两者重复——一旦有人把 yml 路径改对，会出现**双重 `Access-Control-Allow-*` 头**，行为不可预期。

**修复建议**（二选一）：
- 删除 yml 的 `globalcors` 段，统一用 `CorsConfig.java`（推荐，便于集中收敛 origins）；
- 或删除 `CorsConfig.java`，统一用 yml（需修正路径并补 `allow-credentials`），避免两套机制打架。

## 五、💡 其它建议

1. **`InternalTokenFilter` 注入范围**：给**所有**经网关的请求注入 `X-Internal-Token`，逻辑成立（网关是唯一对外入口，BFF/server 再做用户级鉴权）。但需确认域服务 `XInternalTokenInterceptor` 的 token 列表与本处 `internal.auth.tokens` 一致；且**生产必须替换为强随机值并通过部署注入**（当前 yml 明文 `xfjy-internal-dev-token-change-in-prod`，注释已提醒）。
2. **配置命名**：`internal.auth.tokens` 用复数，却只取 `split(",")[0]` 第一个；要么简化为单 token，要么真正实现多 token 支持。

## 七、复盘与纠正：网关全站 404 事故（2026-11-05，修复提交 f83e77a）

### 7.1 事故现象

部署 07a220c（即第六节记录的 CORS 白名单整改）后，网关 `:8090` **所有路径**——`/`、`/admin/login`、`/small-videos`、`/actuator/health/gateway`——统一返回 Spring WebFlux 默认 404（带 `timestamp/path/requestId` 的标准错误 JSON）。容器状态 healthy、端口在听、Nacos 注册正常，进程层面无任何异常，纯路由匹配全灭。

### 7.2 根因（三层）

**① 框架机制：Spring Cloud 2025.x 配置前缀迁移，且旧前缀被静默丢弃**

本项目锁定 Spring Cloud `2025.1.3` + Spring Boot `4.1.1`。Gateway 服务端配置在 2025.x 按运行时拆分为 webflux / mvc 两棵命名空间：

| 版本 | 路由 / 全局 CORS 前缀 |
|---|---|
| **2025.x（本项目，正确）** | `spring.cloud.gateway.server.webflux.routes` / `.globalcors` |
| 旧版 Gateway 4.x / Boot 3.x | `spring.cloud.gateway.routes` / `.globalcors` |

Spring Boot 配置绑定默认 `ignoreUnknownFields=true`：旧前缀 `spring.cloud.gateway.routes` 在 2025.x 没有对应 `@ConfigurationProperties` 绑定目标，会被**静默丢弃，不报错、不告警、不影响启动**。路由表为空后，任何请求 Path 都无匹配 → 统一 404。这是「配置层级错了却毫无启动期信号」的根本原因。

**② 人为诱因：错误的审查结论 + 结构性删除误伤兄弟节点**

- 事故前 f377faf 的 yml 在 `spring.cloud.gateway.server.webflux` 下**平级**放置 `globalcors` 与 `routes`，前缀本就正确（运行时实证见 7.3）。
- 本文件第三节基于 Gateway 4.x 旧知识，误判 `server.webflux` 是「多出来的错误层级、死配置」，主张退回 `spring.cloud.gateway.globalcors`——该判断在 2025.x 下是错的。
- 07a220c 照此删除 `globalcors` 子树时，把它与 `routes` 的**公共父节点 `server:` → `webflux:` 两层 YAML 壳一并删掉**，`routes` 被整体提升到旧前缀 `spring.cloud.gateway.routes`；列表项还残留 12 空格旧缩进。YAML 语法仍合法（能成树、能解析），但语义层级已错，编译期与 YAML 解析均不报错。
- 定性：CORS `allowedOriginPatterns:"*"` + `allowCredentials:true` 过度开放是**真问题**，收敛到 `CorsConfig.java` 白名单的**方向也正确**；错误在于夹带了过时的框架前缀假设，且结构性删除破坏了同层级的 `routes`。正确的安全整改引发了更严重的可用性事故。

**③ 防线失效：现有验证全部测不到配置绑定**

- `mvn compile` 不校验 yml 与 `@ConfigurationProperties` 的绑定关系，对层级错误无感；
- AGENTS §13.7 的 grep 校验只查 CORS 通配符（`addAllowedOriginPattern("*")` / `allowedOriginPatterns: "*"`），覆盖不到路由前缀；
- `deploy/ci/health-check.sh` 仅探测 `8090/admin/` 端口可达（HTTP code ≠ `000` 即判通过），而坏版本返回的是 404（非 000），健康检查照样判绿；
- 缺少「关键路由真正匹配」的冒烟断言（如断言某已知路由不返回 404，或经 actuator 核对已加载路由定义数 > 0）。

### 7.3 运行时实证（双向反证，非文档推测）

同一份 routes 内容，仅前缀层级不同：

- f377faf（`spring.cloud.gateway.server.webflux.routes`）：走网关 admin login 200、`/admin/users/2005/profile-logs` 200，路由生效；
- 07a220c / 3b1f29f（被提升到 `spring.cloud.gateway.routes`）：全路径 404。

一通一不通，坐实 2025.x 的正确前缀就是 `spring.cloud.gateway.server.webflux`，第三节「死配置」判断不成立。

> 方法论：本技术栈（Boot 4 / SC 2025，网上旧资料多为 Boot 3 前缀）排查「配置不生效」，不能凭旧博客或旧经验下结论，应**反编译本地仓库 jar 的 `@ConfigurationProperties` 类确认前缀**，或靠运行时实证（同一配置仅换前缀做对照）。本项目 MongoDB `spring.mongodb.*` 前缀迁移是同类坑（见本地记忆 `project_springboot4_property_migration`）。

### 7.4 修复（f83e77a）

仅编辑 `xfjy-gateway/src/main/resources/application.yml`，把 `routes` 还原到 `spring.cloud.gateway.server.webflux` 下并修正列表缩进（10 空格 `- id:`），与 f377faf 已知良好结构对齐；**不恢复 `globalcors`**——CORS 继续由 `CorsConfig.java` 读取顶层 `cors.allowed-origins` 白名单唯一接管，保留第六节的安全整改成果；顶部白名单与底部 `internal.auth.tokens` 不动。改动 1 文件 +6 −2。

本地验证：node `yaml` 解析确认路由落在正确前缀（2 路由、server 12 个 Path、白名单/token 保留、无 globalcors）；`mvn -o -pl xfjy-gateway -am -DskipTests compile` EXIT=0。

### 7.5 预防建议（待人工裁决，AI 未擅自改规则/脚本）

1. **健康检查升级**：`health-check.sh` 把「端口非 000」收紧为「断言已知路由不返回 404」，例如期望 `:8090/actuator/health/gateway` 返回 200，或对一个固定业务路由断言 `code != 404`，让路由表为空这类静默失效在 CI 阶段直接失败。
2. **规则固化**：建议在 AGENTS.md §13.7（或 §1 技术栈）补一条强制——网关路由与全局 CORS 前缀必须是 `spring.cloud.gateway.server.webflux.*`，禁止退回无 `server.webflux` 的旧前缀；并加一条对应 grep 校验。AGENTS.md 由人维护，需走 PR「规则变更理由」流程。
3. **结构性删除纪律**：删 YAML 子树时核对是否与相邻节点共享父级，删除后用 YAML 解析打印目标属性路径（本次即用 node `yaml.parse` 验证），不要只看缩进。
4. **审查知识时效**：涉及 Boot 4 / SC 2025 新增/迁移的配置项，结论须附 jar 反编译或运行时证据，不得仅凭旧版经验判定「死配置」。
