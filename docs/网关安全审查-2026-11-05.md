## 二、🔴 严重问题：CORS 允许任意来源携带凭证

**位置**：`CorsConfig.java`

```java
config.addAllowedOriginPattern("*");   // 允许任意来源
config.setAllowCredentials(true);      // 且允许携带凭证（Cookie / token）
```

**风险**：任意第三方网站在用户已登录状态下，均可借浏览器凭证直接调用 API（发动态、改资料等），构成 CSRF / 跨站数据泄露风险。

**修复建议**（二选一）：
1. 若前端仅用 `Bearer` Token（Sa-Token 默认）：`setAllowCredentials(false)` 并收窄 `addAllowedOriginPattern` 到前端域名白名单（如 `http://localhost:5173`、生产域名）。
2. 若确需凭证：至少将 origins 限定为前端已知域名，禁止 `*`。</n>
**规范关联**：AGENTS.md §二 安全防护要求“所有用户输入均视为高危，必须校验与异常捕获”；CORS 全开属于放宽同源策略的过度授权，应最小权限化。

## 三、🟡 配置错误：`globalcors` 路径写错 + 与代码重复

**位置**：`application.yml`

```yaml
spring:
  cloud:
    gateway:
      server:
        webflux:
          globalcors:   # 错误：多了一层 server.webflux，绑定不到 GatewayProperties
```

正确路径应为 `spring.cloud.gateway.globalcors.cors-configurations`。当前这段配置**完全不生效**（死配置）。

**衍生风险**：同时 `CorsConfig.java` 已用 `CorsWebFilter` 实现了一套 CORS。两者重复——一旦有人把 yml 路径改对，会出现**双重 `Access-Control-Allow-*` 头**，行为不可预期。

**修复建议**（二选一）：
- 删除 yml 的 `globalcors` 段，统一用 `CorsConfig.java`（推荐，便于集中收敛 origins）；
- 或删除 `CorsConfig.java`，统一用 yml（需修正路径并补 `allow-credentials`），避免两套机制打架。

## 五、💡 其它建议

1. **`InternalTokenFilter` 注入范围**：给**所有**经网关的请求注入 `X-Internal-Token`，逻辑成立（网关是唯一对外入口，BFF/server 再做用户级鉴权）。但需确认域服务 `XInternalTokenInterceptor` 的 token 列表与本处 `internal.auth.tokens` 一致；且**生产必须替换为强随机值并通过部署注入**（当前 yml 明文 `xfjy-internal-dev-token-change-in-prod`，注释已提醒）。
2. **配置命名**：`internal.auth.tokens` 用复数，却只取 `split(",")[0]` 第一个；要么简化为单 token，要么真正实现多 token 支持。
