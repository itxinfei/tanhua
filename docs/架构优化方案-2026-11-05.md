## 二、优化目标

| 目标 | 衡量标准 |
|------|---------|
| **G1 安全边界硬隔离** | 宿主机仅暴露 8090；域服务端口 0 映射 |
| **G2 鉴权链完整** | 内部 Token 支持多值注入与校验，生产强随机值 |
| **G3 BFF 薄编排化** | Admin 业务与 C 端编排解耦，BFF 不再持有 Admin 领域逻辑 |
| **G4 推荐引擎目标态** | 双塔 + 向量召回为主，ALS 降为协同信号之一，可灰度可回退 |
| **G5 技术债清零** | 死代码/重复实现/规范偏离全部闭环 |

## 三、优化方案（按优先级）

### 阶段一：安全与边界收敛（P0，1~2 天）

#### A1. 删除域服务端口映射

**改动文件**：`deploy/docker-compose.app.yml`

```yaml
# 删除以下服务的整个 ports 段（保留 gateway 8090）：
#   xfjy-sso (18080) / xfjy-user-service (18090) / xfjy-circle-service (18084)
#   xfjy-video-service (18085) / xfjy-match-service (18082) / xfjy-message-service (18086)
#   xfjy-server (18081) / xfjy-recommend (18087) / xfjy-elasticsearch (18088) / xfjy-pay-service (18089)
```

**配套**：新增 `deploy/docker-compose.override.dev.yml`（**不入库**，加入 `.gitignore` 或 `deploy/.gitignore`），供本地调试按需放开端口：

```yaml
# 本地调试用：docker compose -f docker-compose.app.yml -f docker-compose.override.dev.yml up -d
services:
  xfjy-server:
    ports: ["18081:18081"]
  # 按需放开其它服务
```

**验证**：`rg -n '^\s+- "\d+:\d+"' deploy/docker-compose.app.yml` → 仅 `8090:8090` 一行。

**风险**：本地调试需 `docker exec` 或 override 文件；Gitea Actions 部署流程不受影响（容器间走 `xfjy-app-net`）。

#### A2. 内部 Token 多值注入

**现状**：拦截器（`xfjy-api/XInternalTokenInterceptor`）已支持 `Set<String>` 多值校验；但网关注入与 BFF 注入均只取第一个。

**改动文件**：

| 文件 | 改动 |
|------|------|
| `xfjy-gateway/.../InternalTokenFilter.java` | 注入时遍历全部 token，用 `header(...)` 追加（Spring 的 `header` 会覆盖，需改用 `headers(consumer -> consumer.add(...))`） |
| `xfjy-server/.../HttpServiceProxyConfig.java` | `builder.defaultHeader` 改为循环注入全部 token |
| `xfjy-server/.../config/VideoSearchClientConfig.java` | 同步（ES 专用客户端也需注入） |

**关键实现**（网关）：

```java
// 多 token 注入：遍历 Set 全部注入
ServerHttpRequest mutated = exchange.getRequest().mutate()
        .headers(headers -> {
            for (String t : internalAuthTokens) {
                headers.add("X-Internal-Token", t);
            }
        })
        .build();
```

**注意**：HTTP 同名头多值在 Servlet 侧 `request.getHeader()` 只取第一个，但网关→BFF 的调用中，BFF 作为下游会收到多值头。BFF 侧无需读取该头（它自己注入），仅需保证透传。**多值的价值在 Token 轮转**：新旧 Token 同时有效，网关同时注入，域服务校验任一即可。

**验证**：`rg -n 'split(",")\[0\]' xfjy-gateway xfjy-server` → 0 命中。

### 阶段二：代码健康度（P1，1 天）

#### B1. IdService 去重

**现状**：两份 IdService 均已用 Lua 原子实现，功能等价。**建议不删除**，理由：
- 分属两个域服务，各自独立演进（如未来 video 需要不同 ID 策略）
- 删除需跨服务改动，收益低、风险中
- 可在两份文件头加注释互相指向，避免后人误判

**决策**：**保留双份，补注释**。若未来出现第三份再考虑抽公共。

---

#### B2. VideoController capPageSize 口径确认

**待确认**：`VideoController.java:52` 上限 50 是否为视频列表性能保护的有意设计。

**决策**：若有意 → 保留并补注释说明；若无 → 统一到 `ParamConvertUtils.capPageSize`（上限 100）。

**验证**：`rg -n "capPageSize" xfjy-server/src` → 确认调用点。

#### B3. 删除环信残留死代码

### 阶段三：BFF 瘦身（P2，3~5 天，渐进）

#### C1. Admin 业务下沉策略

**现状**：`xfjy-server` 30 个 Controller 中 16 个是 `Admin*`，承载全部后台业务。

**方案**：**不新增服务**，而是将 Admin Controller 与对应 Service 下沉到各域服务，经 BFF 路由转发。但这涉及跨服务调用链改造，成本高。

**更务实的方案（推荐）**：
- **保持 Admin 在 BFF**，但将 C 端编排逻辑与 Admin 业务在包结构上隔离（`controller/app/` vs `controller/admin/`）
- 将推荐打分（`RecommendScoringService` + `ReciprocalScoringService`）下沉到 `xfjy-recommend` 服务，BFF 通过 API 调用
- 将对象存储（MinIO）上传逻辑下沉到独立的工具服务或保留（低频操作，可接受）

**落地步骤**：
1. 包重构：`xfjy-server` 内按 `app/` 与 `admin/` 分包（仅移动，不改逻辑）
2. 推荐打分下沉：`RecommendScoringService` → `xfjy-recommend`，暴露 `POST /api/recommend/score` 接口
3. BFF 调用 recommend API 获取分数，不再内联

**收益**：BFF 代码量减少 ~15%，推荐逻辑内聚到 recommend 服务。

**风险**：接口新增，需前端无感知（BFF 内部调用，契约不变）。

### 阶段四：推荐引擎目标态（P3，独立立项，5~8 天）

#### D1. 现状（已具备双塔基建）

```
xfjy-recommend (MQ 消费者)
  → MongoDB recommend_quanzi_yyyyMMdd（ALS 评分数据源）
  → UserFeatureService（特征宽表增量，双塔数据源）✅ 已就绪

xfjy-recsys (PyTorch 双塔)
  → embeddings.json → Qdrant(user_embedding) ✅ 已就绪

xfjy-server (BFF)
  → RecommendScoringService：ALS + 地理 + 画像 + 互惠 + 社交 混合评分 ✅ 已就绪
  → ReciprocalScoringService：Qdrant cosine² 互惠分 ✅ 已就绪
```

**结论**：阶段 1（混合评分）+ 阶段 2 的部分基建（双塔 + Qdrant 召回）**已落地**。剩余工作：

| 缺口 | 说明 |
|------|------|
| 双塔模型未实际训练/灌库 | `xfjy-recsys` 代码就绪，但生产 Qdrant 可能无 embedding（`xfjy.qdrant.enabled=false`） |
| 召回未走 Qdrant ANN | 当前候选仍来自 ALS 列表，Qdrant 只做精排互惠分 |
| ALS 依赖未解除 | `recommend_user` 表仍是候选来源 |

#### D2. 目标架构

```
用户请求 → BFF → xfjy-recommend
  ├─ 1. 召回：Qdrant ANN Top-K（用户 embedding → 近邻）
  ├─ 2. 粗排：地理距离 + 活跃度过滤
  ├─ 3. 精排：混合评分（双塔互惠 + ALS 协同 + 画像 + 社交）
  ├─ 4. 冷启动：画像 embedding 兜底（新用户）
  └─ 5. 缓存：Redis → 对外接口
```

#### D3. 落地步骤

| 步骤 | 内容 | 验证 |
|------|------|------|
| D3-1 | 生产环境开启 Qdrant（`xfjy.qdrant.enabled=true`）+ 灌入全量 embedding | Qdrant collection `user_embedding` 有数据 |
| D3-2 | `xfjy-recommend` 新增召回接口：读 Qdrant ANN → 返回候选 ID 列表 | 接口返回候选数 ≥ 20 |
| D3-3 | `RecommendScoringService` 候选来源切换为 Qdrant 召回（保留 ALS 为降级通道） | 灰度开关 `xfjy.recommend.recall-source: qdrant\|als` |
| D3-4 | 冷启动兜底：无 embedding 用户用画像向量召回 | 新用户有推荐结果 |
| D3-5 | 下线 ALS 主输入（保留为协同信号维度） | Spark 相关代码可删除 |

**灰度策略**：`xfjy.recommend.recall-source` 配置切换，先 10% 流量走 Qdrant，观察匹配率/滑动率后全量。

**回退**：配置切回 `als` 即可，无需回滚代码。

## 四、技术决策依据

| 决策点 | 备选 | 选定 | 依据 |
|--------|------|------|------|
| 域服务端口 | 保留映射 + 防火墙 | 删除映射，仅 8090 | CONST-ARCH-002 MUST；容器网络已隔离；调试用 override |
| 内部 Token | 简化单值 | 多值注入 | 拦截器已支持多值；轮转需求真实；规范 27 号已定义 |
| IdService | 删除一份 | 保留双份 + 注释 | 两份均已 Lua 原子，功能等价；分属不同域，独立演进 |

| CORS | 修正 yml 路径 | 保留 Java 代码 | 代码方式支持动态白名单；yml 路径已证明易错 |

## 六、不做什么（明确排除）

| 排除项 | 理由 |
|--------|------|
| 拆 Admin 为独立微服务 | 成本高、部署单元膨胀；个人项目规模不适用 |
| 引入服务网格（mTLS） | 当前共享 Token + 容器网络隔离足够；YAGNI |
| 拆 BFF 为多个网关 | 单 BFF 足够；拆分增加调用链复杂度 |
| 删除 ALS 全部代码 | ALS 作为协同信号维度仍有价值；保留降级通道 |
| 更换 WuKongIM/LiveKit | 已端到端验证；切换成本高于收益 |
