> 版本：v0.1（草案，待评审）
> 创建日期：2026-10-24
> 状态：需求分析中
> 范围：推荐引擎（xfjy-recommend + xfjy-spark）整体重构，从 Spark MLlib ALS 迁移至「双塔模型 + 向量检索 + 互惠匹配」
> 关联文档：`docs/需求文档.md`、`docs/项目重构规划.md`、`docs/升级任务计划.md`、`docs/功能就绪矩阵.md`

## 一、背景与现状

### 1.1 现有推荐链路

```
用户行为（发布/浏览/点赞/喜欢/评论）
    │ RocketMQ（xfjy-quanzi / xfjy-video）
    ▼
xfjy-recommend（MQ 评分消费者）→ MongoDB 按日分集合（recommend_quanzi_yyyyMMdd / recommend_video_yyyyMMdd）
    ▼
xfjy-spark（Spark MLlib ALS 离线计算）→ MongoDB recommend_user 集合
    ▼
Redis 缓存 → 接口消费（今日佳人 / 推荐列表 / 探花卡片 / 推荐动态 / 推荐视频）
```

### 1.2 现有行为评分规则（保留复用）

| 行为类型 | type | 评分 |
|----------|------|------|
| 发布动态 | 1 | 1~3 分（按文字长度）+ 图片数量加分 |
| 浏览动态 | 2 | +1 |
| 点赞 | 3 | +5 |
| 喜欢 | 4 | +8 |
| 评论 | 5 | +10 |
| 取消点赞 | 6 | -5 |
| 取消喜欢 | 7 | -8 |

### 1.3 ALS 方案的四个结构性短板（重构动因）

| # | 短板 | 说明 |
|---|------|------|
| 1 | 冷启动无解 | 只吃 user-item 交互矩阵，新用户/新注册用户无行为数据即无法推荐 |
| 2 | 不建模互惠匹配 | 交友推荐是双向的，ALS 只预测单向喜欢，需后处理启发式补救（Hinge 论文同款痛点） |
| 3 | 浪费画像特征 | 年龄/性别/城市/学历/收入/行业/签名/位置等核心信号 ALS 全部用不上 |
| 4 | 运维重 | 为个人项目规模维护 Spark 集群成本高；且稀疏数据下 ALS 易过拟合 |

### 1.4 重构目标

- **G1**：推荐引擎切换为「双塔模型（Two-Tower）+ 向量检索」，支撑"人找人"的用户推荐、动态推荐、视频推荐三类场景。
- **G2**：建模互惠匹配，推荐"对我也感兴趣"的人（p(like) × p(recip)）。
- **G3**：解决冷启动：新用户用画像 embedding 兜底，无需等待行为数据。
- **G4**：Spark 退役，降低运维负担（删除 xfjy-spark 模块或降级为可选）。
- **G5**：现有对外接口不变（今日佳人/推荐列表/卡片/推荐动态/推荐视频），内部数据源平滑切换。

### 1.5 非目标（本迭代不做）

- 不做重排序大模型（DeepFM/DIN 精排）：当前数据量未达阈值，作为阶段 3 预留。
- 不做 Spark Streaming 实时流式推荐。
- 不引入 LLM 语义推荐（URM 等）：个人项目规模不适用。

## 二、总体技术方案

### 2.1 目标架构

```
                    离线训练（Python，定时/事件触发）
用户行为 + 画像特征 ──→ 双塔模型（LibRecommender / PyTorch）
                              │ 产出
                              ▼
             用户 embedding / 画像 embedding ──→ 向量库（Qdrant 单机 / FAISS）
                                                    │ ANN 近邻召回
在线推荐（Java 侧，xfjy-recommend 重构）
   用户请求 ──→ 读取用户 embedding ──→ 向量库 Top-K 召回
              ──→ 互惠匹配打分 p(like) × p(recip) + 规则加权（距离/活跃度/画像相似度/desirability）
              ──→ 冷启动兜底（画像 embedding / 默认推荐列表）
              ──→ Redis 缓存 → 对外接口
```

### 2.2 三阶段演进路线

| 阶段 | 方案 | 改动量 | 说明 |
|------|------|--------|------|
| 阶段 1（保底） | 混合评分：ALS 分数降为协同信号之一，与地理位置/活跃度/画像相似度加权融合 | 小 | 1-2 天见效，先保证推荐可用 |
| 阶段 2（目标态） | 双塔模型 + 向量检索：画像/行为 → embedding → 近邻召回 → 双向概率排序 | 中 | 核心升级，Spark 退役 |
| 阶段 3（预留） | 召回 + 精排两阶段：向量召回 + DeepFM/DIN 精排 | 大 | 数据量上来后启用 |

> 决策：**直接以阶段 2 为目标态设计代码结构**（按"embedding 召回 + 精排"分层），阶段 1 的混合评分作为阶段 2 未就绪时的降级通道，避免二次返工。

### 2.3 关键技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 训练框架 | LibRecommender（首选）/ PyTorch 自写 | 一站式含 TwoTower/ALS/DIN，中文生态好 |
| 向量库 | Qdrant 单机（首选，Docker 部署）/ FAISS 库 | 个人项目规模 10K~1M 向量单机足够，不引入 Milvus |
| 互惠匹配 | 双塔双向建模 | p(like) 与 p(recip) 独立塔输出，match = p(like) × p(recip)（Hinge 论文做法） |
| 冷启动 | 画像 embedding 兜底 | 年龄/性别/城市/MBTI/兴趣标签 → 向量，行为数据不足时直接用画像向量召回 |
| 精排信号 | desirability（被右滑率）+ 距离 + 活跃度 + 资料完整度 | 规则加权，阶段 3 可替换为模型精排 |
| 训练触发 | 每日定时 + 行为量阈值事件触发 | 复用现有 RocketMQ 链路收集行为 |

## 三、功能需求

### FR-ENGINE-R01 行为数据采集（保留现有）
- **描述**：沿用现有 RocketMQ 评分链路（`xfjy-quanzi` / `xfjy-video`），评分规则不变（见 1.2）。
- **变更**：`xfjy-recommend` 消费者在写评分集合的同时，**冗余写入行为明细集合**（供双塔训练取数），字段：userId、targetId（用户/动态/视频）、behaviorType、score、timestamp、上下文（位置/时段）。

### FR-ENGINE-R02 特征工程
- **输入**：`tb_user_info`（年龄/性别/城市/学历/婚姻/收入/行业/签名/照片）、行为明细、ES 位置。
- **输出**：用户特征宽表（MongoDB `user_feature` 集合），字段：静态画像 + 统计特征（活跃度、互动数、被喜欢数、desirability 分）+ 行为序列摘要。
- **验收**：特征宽表可被训练脚本直接读取；新用户注册即有画像向量（冷启动就绪）。

### FR-ENGINE-R03 双塔模型训练（Python 离线）
- **训练目标**：预测用户 u 对候选用户 v 的喜欢概率 p(like) 与 v 对 u 的互惠概率 p(recip)。
- **样本**：正样本 = 喜欢/匹配成功记录；负样本 = 不喜欢/未互动用户对（负采样）。
- **产出**：
  - 用户 embedding（含画像 embedding 与行为 embedding 两种来源）
  - 互惠匹配打分模型（match = p(like) × p(recip)）
- **输出物**：embedding 文件/向量写入脚本 → 向量库。
- **验收**：离线评估 Recall@K 优于 ALS 基线（用现有 recommend_user 结果做对比基线）；模型产物版本化可回滚。

### FR-ENGINE-R04 向量召回（Java 侧）
- **接口**：`POST /engine/recall`（内部），输入 userId + 场景（user/movement/video），输出 Top-K 候选及相似度。
- **实现**：Qdrant/FAISS 查询用户 embedding 的近邻；按场景过滤（用户推荐过滤已滑过/已拉黑/非同城可配置）。
- **验收**：P95 召回延迟 < 100ms；结果与训练侧评估一致。

### FR-ENGINE-R05 互惠匹配打分与精排
- **打分**：candidate score = w1·互惠匹配分 + w2·相似度 + w3·距离衰减 + w4·活跃度 + w5·desirability + w6·资料完整度（权重可配置）。
- **互惠匹配分**：来自双塔模型的 match 概率（行为充足用户）；冷启动用户退化为画像相似度。
- **验收**：打分公式参数配置化（YAML），可灰度调整；输出可解释（记录各分项）。

### FR-ENGINE-R06 冷启动兜底
- **新用户（无行为）**：用画像 embedding 召回 → 过滤 → 规则排序。
- **新动态/新视频（无交互）**：用内容特征向量召回 + 时间衰减保底。
- **兜底链**：双塔召回 → 画像召回 → 热门/默认推荐（现有 default users 配置保留）。
- **验收**：新注册用户首次进入匹配页即有可滑动卡片（不允许空列表）。

### FR-ENGINE-R07 在线接口兼容
| 现有接口 | 数据源切换 | 说明 |
|----------|-----------|------|
| `GET /xfjy/todayBest` | 推荐结果最高分 | 缓存策略保留 |
| `GET /xfjy/recommendation` | 推荐列表 | 分页/性别筛选保留 |
| `GET /xfjy/cards` | 推荐列表 Top-N | 探花卡片 |
| `GET /movements/recommend` | 动态召回结果 | 推荐动态流 |
| `GET /smallVideos` | 视频召回结果 | 推荐视频流 |
- **验收**：上述接口响应结构完全不变，前端零改动。

### FR-ENGINE-R08 模块重构
- `xfjy-recommend`：保留 MQ 消费职责，新增「召回 + 打分」在线推荐能力（或拆分出 `xfjy-recommend` 在线查询与训练产物加载）。
- `xfjy-spark`：**退役**（删除模块 + 根 pom module 移除 + README 更新）；若需保留 ALS 基线对比，移入 Python 侧实现。
- **验收**：`mvn compile` 全模块通过；无 Spark 依赖残留。

## 四、非功能需求

| 指标 | 要求 |
|------|------|
| 召回延迟 | P95 < 100ms（在线推荐） |
| 推荐接口响应 | P95 < 500ms（缓存命中 < 50ms） |
| 训练频率 | 每日定时 + 行为量阈值触发（增量训练） |
| 容量 | 支持 10K~1M 向量单机（Qdrant/FAISS） |
| 数据一致性 | 行为 → 特征 → embedding 全链路幂等，可重跑 |
| 可回滚 | 模型产物版本化；向量库索引可重建；旧推荐结果保留 N 天 |
| 可观测 | 召回率/匹配率/冷启动命中率指标打点（Prometheus 预留） |

## 五、数据模型变更

### 5.1 MongoDB

| 集合 | 说明 | 变更 |
|------|------|------|
| `recommend_quanzi_yyyyMMdd` / `recommend_video_yyyyMMdd` | 行为评分（按日分集合） | 保留（评分规则不变） |
| `recommend_user` | ALS 推荐结果 | 退役（不再写入；历史数据保留 N 天） |
| `behavior_detail` | 行为明细（训练取数） | **新增** |
| `user_feature` | 用户特征宽表 | **新增** |
| `user_embedding` | 用户 embedding（含画像/行为两种来源） | **新增**（或直写向量库，Mongo 留备份） |

### 5.2 向量库（Qdrant / FAISS）

| Collection / Index | 向量维度 | 说明 |
|--------------------|----------|------|
| `user_vector` | 64~128（可配） | 用户近邻召回；payload 存性别/城市/活跃度用于过滤 |
| `movement_vector` | 64~128 | 动态内容向量（阶段 3 可启用） |
| `video_vector` | 64~128 | 视频内容向量（阶段 3 可启用） |

### 5.3 Redis

| 键模式 | 用途 | 变更 |
|--------|------|------|
| `recommend::user:{userId}:{scene}` | 在线推荐结果缓存 | **新增**（TTL 1 小时） |
| `recommend::model:{version}` | 当前模型版本标记 | **新增** |
| 现有用户资料/公告缓存 | — | 不变 |

## 七、风险与对策

| 风险 | 等级 | 说明 | 对策 |
