# 心飞交友后台管理系统 · 优化修复计划

> 创建：2026-10-30 | 基于 xfjy-admin（Vue3 + TS + Vite + Element Plus + Pinia）+ xfjy-server 全量只读诊断
> 状态：**待确认**（本计划经确认后分阶段实施）
> 范围：功能设计缺陷 + UI 视觉 + 性能，含前端与后端联动改造

---

## 〇、结论概要（先看这个）

后台系统**功能完整但"不好用"的根因不是缺页面，而是四类系统性问题**：

1. **权限（RBAC）完全缺失** —— 最严重。后端拦截器只校验登录态，三级角色无接口级鉴权；前端路由/菜单/按钮均不按角色过滤。任何登录账号都能审核、封禁、下架套餐、刷新词库、查看管理员名录。
2. **"UI 在，数据假"** —— 看板 DAU=总用户数、匹配率/付费率/动态总数=硬编码 0，前端却画成真实曲线；多个页面 DEV 兜底假数据。
3. **核心业务是"半成品 CRUD 表格"** —— 审核工作台无队列/快捷键、视频无法审核、举报证据图不渲染、内容管理只有删除。
4. **体验与规范碎片化** —— 每个列表页一套样式/工具函数/分页命名/时间格式；失败与空数据不可区分；无响应式；ECharts 泄漏。

修复顺序按 **安全 → 数据真实性 → 核心业务效率 → 全局规范 → 细节** 推进，每阶段独立可验证。

## 二、根因分析

- **权限**：后端采用 Sa-Token 但只做了登录态拦截，未接 `@SaCheckRole` 注解体系；前端未建立 `roles` 元数据 → 权限指令 → 菜单过滤的链路。属"一开始就没做"而非"退化"。
- **数据假**：看板统计依赖 Redis/Mongo 的 DAU、匹配、付费指标，后端占位返回 0；前端为"好看"先画曲线，无"数据为空则不画"的降级逻辑。属"占位实现 + 前端不感知空值"双重叠加。
- **半成品 CRUD**：各页先完成列表 + 删除的最小闭环即算"完成"，审核/举报/内容治理的完整状态机、批量、证据链属遗漏，非设计如此。
- **规范碎片化**：无 `design-tokens`/全局工具库，各页按需自写，导致同质代码 6+ 份、样式 2 套体系。

## 三、修复方案（分 6 阶段，每阶段可独立验证）

### 阶段 0：权限底线（RBAC）—— 最高优先

**后端**（`xfjy-server`）
1. 在 `AdminTokenInterceptor` 或新增 `@RequireRole` 注解 + 切面中，建立**角色矩阵**，统一鉴权而非散落各 Controller：
   - `SUPER_ADMIN`：全部
   - `ADMIN`：审核、举报处理、内容管理、公告、客服、日志
   - `OPERATOR`：审核、举报处理、客服（只读）、日志（只读）—— 或**直接砍掉 OPERATOR 空角色**，二选一由你定
2. 给 `AdminAccountController` 的 `GET /admin/accounts` 补 `@RequireRole(SUPER_ADMIN)`（堵住越权读取）；`PUT /admin/password`、`PUT /admin/profile` 放行给登录者本人。
3. `resetPassword` 后调 `StpUtil.logout(id)` 强制对方重新登录。

**前端**（`xfjy-admin`）
4. `router/index.ts` 路由 `meta.roles` 标注；守卫按 `authStore.adminInfo.role` 校验，无权跳 403/首页。
5. `Sidebar.vue` 按 `meta.roles` 过滤菜单。
6. 新增全局指令 `v-perm="'role:xxx'"` 控制按钮级显隐；给审核/封禁/公告发布/套餐上下架/词库刷新按钮加指令。
7. 登录页/Header 展示真实角色，移除"角色隔离"的宣传语或改为真实描述。

**验证**：用 ADMIN 账号直接访问 `/system/admin` 应 403；OPERATOR 看不到审核外菜单；被重置密码者立即掉线。

---

### 阶段 1：数据真实性

1. **看板**（`AdminDashboardService` + `dashboard/index.vue`）
   - 后端：DAU 接入登录日志/Redis 统计；匹配率、付费率、动态总数接入真实数据源；无法实时统计的字段，明确改为"暂无数据"占位。
   - 前端：`trend` 返回全 0 时**不画曲线**，显示空态提示"数据待接入"；数字加千分位；修复 ECharts `dispose` 泄漏。
2. **清除 Mock 兜底**：`user/detail.vue` 删掉生产环境回填假用户；`user/index.vue`、`dashboard`、`review/report/notice` 的 DEV mock 统一改为"失败 → 错误态 + 重试按钮"，不造假数据。
3. **全局错误态**：抽 `PageState`（空/错误/加载）统一组件或 mixin，替换各页"catch 置空"。

**验证**：接口失败时各页显示"加载失败 + 重试"，不再出现假用户/假曲线。

---

### 阶段 2：核心业务效率（审核 / 举报 / 内容 / 客服）

1. **审核工作台重构**（`review/index.vue`）：队列式作业——键盘快捷键（A 通过 / R 驳回 / ←→ 上下条 / 空格预览）、详情抽屉（长文 + `<video>` 播放 + 大图预览）、处理后自动下一条、单条通过取消强制确认、跨页批量、可点发布者看历史违规、回显 `reviewer/reviewedAt/rejectReason`。
2. **举报证据链**（`report/index.vue`）：详情弹窗渲染 `evidence` 图组、按 `targetType` 展示/跳转被举报内容本体、封禁拆为（警告/删除内容/限时封禁/永封）+ 强制备注、接通闲置的 `getReportDetailApi/batchHandleReportApi`、补 PROCESSING 状态。
3. **内容管理闭环**（`content/{movement,video,comment}.vue` + 后端）：补审核状态流转（通过/驳回/隐藏/恢复）、`seeType` 列与筛选、举报数列与排序、批量操作、软删除替代物理删除。
4. **客服 IM 三硬伤**（`workbench.vue` + `KefuService.java` + `easemob.ts`）：
   - 多客服 → 每管理员独立环信 ID（凭证按登录人下发，替换硬编码 `kefu0001`），监听 `onConnected/onDisconnected` 做状态与重连；
   - 打开会话发已读回执（`markConversationRead`），清会话未读与总未读；
   - 历史消息接入 `cursor/hasMore` 向上分页；图片/语音至少显示"[图片]/[语音]"占位不丢弃；输入框支持多行。

**验证**：审核员连续处理 50 条不碰鼠标；举报页能看图判定；视频能播放审核；两个客服同时在线不互踢。

### 阶段 3：全局 UI 规范（设计令牌 + 公共组件）

1. 建 `src/styles/tokens.scss`（主色/圆角/间距/阴影/状态色语义）与 `src/styles/index.scss`，替换散落的 `#409eff/#001529` 等硬编码。
2. 抽公共组件：`PageTable`（含 `.page-container > .search-bar > .table-container > .pagination-wrapper` 骨架）、`StatusTag`、`EmptyState`、`TimeText`。
3. 抽全局工具：`formatTime`、`formatAmount`（千分位）、`statusLabel/Color` 映射，收敛 6+ 份重复。
4. 统一页面结构：admin/log/profile/content 全部改用公共骨架。
5. 响应式：看板 `el-col` 加 `:xs/:sm/:md` 断点；个人中心、详情页同理。
6. 修复 `Breadcrumb.vue`（首页判定改用路由 name 而非文案匹配；父级可点击跳转）；404 页视觉对齐全站风格。

**验证**：全站主色/圆角/卡片一致；1366px 下看板不横向滚动；不同页面同状态颜色语义一致。

### 阶段 4：功能补齐（低危项）

1. 公告：OFFLINE 可重新发布（补状态流转）、内容支持富文本/预览、发布后编辑走"转草稿"确认。
2. VIP：上下架加二次确认、等级/时长互斥校验、金额改元为单位 + 千分位、权益展示"等级×权益"矩阵。
3. 支付：加时间范围筛选、订单汇总、导出、订单号复制、流水号字段。
4. 敏感词：批量导入/导出、命中测试框（输入一句话看命中的词与动作）、刷新按钮加确认 + 结果反馈。
5. 反馈：加用户ID/关键词/时间筛选、展示昵称（复用 `getKefuUsersInfoApi`）、回复历史、关闭后可重新打开。
6. FAQ：加关键词搜索、分类改字典接口（不再前端写死）、category 必填校验、启停加确认。
7. 操作日志：加 action 筛选、详情弹窗（可复制 JSON）、导出、日期快捷项。
8. 用户列表：接注册时间范围筛选（`UserQuery` 已定义未用）、批量封禁/解封、VIP/城市筛选。
9. 个人中心：状态读真实值、头像支持上传、角色颜色统一。

**验证**：逐页功能点测，重点覆盖各状态机分支与批量操作。

## 五、风险与注意事项

1. **RBAC 改动会影响所有登录者**：上线前需明确角色矩阵并准备测试账号；OPERATOR 若无法定义差异权限，建议先移除该角色避免"空标签"。
2. **客服 IM 改造涉及环信账号体系**：多客服独立 ID 需后端凭证接口按登录人签发，改造期间避免与现网 `kefu0001` 冲突。
3. **数据真实化后看板短期会"变空"**：属预期（从假变真），需向使用者说明，避免误判为故障。
4. **前端权限隐藏 ≠ 安全**：按钮级 `v-perm` 只是体验，安全边界必须由后端鉴权兜底，二者缺一不可。
5. 涉及 `docker-compose`、生产环境、数据库 DDL 的改动一律先确认环境（dev/test/prod）再执行。
6. 每个阶段完成后提供验证命令与预期结果（如：用 ADMIN 访问 `/system/admin` 预期 403），跑通才算完成。
